# v0.25 Reward Clarity, Combat Readability, and Control Tuning Plan

Status: Implemented in v0.25.0.

## Playtest Notes

- Permanent rewards are too rare or appear too late.
- The player needs frequent permanent reward opportunities, especially early.
- Caught pickups do not clearly explain what they did.
- Auto-collect on level clear is mechanically useful but not visually obvious.
- Temporary rewards feel wonky, especially from stage-clear choices.
- Temporary and permanent reward identity is not readable enough.
- The current temporary indicator placement near the top-right HUD is not a good fit.
- Lives are mechanically important but not emotional or readable enough.
- Losing a life or consuming a shield can happen too quietly.
- Bosses, especially Level 10, can attack too often and kill the run too early.
- Cannon use needs a better input and a much clearer ready/locked indicator.
- The paddle should be made smaller as a balance pass.

## Goals

- Target desktop play at 1080p first.
- Make permanent progression feel reliable every level.
- Make every pickup explain itself immediately.
- Make auto-collected rewards feel intentional, not invisible.
- Make temporary and permanent reward state readable without crowding the playfield.
- Remove coin rewards from in-level and stage-clear reward pools until that system actually exists.
- Use the stage-clear screen as a second-chance permanent roll when no permanent upgrade was earned in the level.
- Replace plain lives text with clearer heart-based health.
- Make life loss and shield saves visibly animated.
- Reduce early boss attack frequency so the player has more room to play brick-breaker.
- Move cannon firing to `Space` and make cannon readiness obvious.
- Reduce paddle width by one-third and verify the new difficulty feel.

## 1. Permanent Reward Frequency

Decision:
- Move to a level-based permanent reward chance in v0.25 instead of a guaranteed permanent block every level.
- Early levels should still be very likely to include a permanent reward.
- Later levels should have lower permanent odds so scaling does not run away too quickly.

Implementation direction:
- Roll a permanent reward chance when generating each level.
- If the roll succeeds, add one permanent reward block to that level.
- If the roll misses, the level has no permanent reward block.
- Keep additional reward blocks for run upgrades, temporary pickups, or special stage identity.
- Boss levels can still have special tuning, but should follow the same readable chance system unless playtests prove they need a bonus.

Suggested reward layout:
- Regular levels with successful permanent roll: 1 permanent block + 1 optional non-permanent reward block when level size allows.
- Regular levels with missed permanent roll: 1-2 non-permanent reward blocks.
- Boss levels: roll permanent chance + 1-2 run/temporary reward blocks.
- Very tiny early levels: if the permanent roll succeeds, convert one brick into the permanent reward block rather than adding extra clutter.

Permanent reward chance curve:
- Level 1: 99% permanent reward chance.
- Level 10: 90% permanent reward chance.
- Level 50: 50% permanent reward chance.
- Levels between anchors should interpolate smoothly.
- Exact values should stay easy to tune after v0.25 playtesting.

Stage-clear backstop:
- If the player did not earn a permanent upgrade during the level, roll the same permanent chance again at stage clear.
- If that second-chance roll succeeds, show a permanent upgrade on the stage-clear screen.
- If that second-chance roll misses, show temporary upgrade choices instead.
- If the player already earned a permanent upgrade during the level, stage-clear should show temporary upgrade choices only.

Acceptance criteria:
- The permanent reward chance follows the configured curve.
- Level generation can produce permanent reward blocks according to that chance.
- Stage clear performs a second-chance permanent roll only when no permanent upgrade was earned in the level.
- The player sees frequent permanent progression early, without guaranteeing permanent power every level.

## 2. Pickup Explanation Text

Decision:
- When a pickup is caught, visible text should float upward from the paddle area toward the top of the playfield.

Behavior:
- Text begins near the paddle or pickup catch position.
- Text floats upward and fades over about 1.2-1.6 seconds.
- Text uses the reward category color.
- Text must be short and readable.

Examples:
- `Permanent: Crit Core`
- `Run: Stonebreaker`
- `Temp: +3 Balls (2 levels)`
- `Shield: +1`
- `Auto: Storm Relay`

Implementation direction:
- Reuse or formalize `level.floatingTexts`.
- Add `ParticleSystem.floatingText()` or a dedicated `FloatingTextSystem`.
- Render floating texts above gameplay entities but below menus/HUD.

Acceptance criteria:
- Catching any pickup shows a readable reward text.
- Choosing a stage-clear bonus also shows a short confirmation.
- Text does not overlap buttons or block paddle visibility for too long.

## 3. Auto-Collect Clarity

Problem:
- If a level ends while a pickup is still falling, the player may not know they got it.

Decision:
- Auto-collected pickups should create the same reward text, prefixed or styled as auto-collected.

Behavior:
- On clear, active falling pickups snap/arc toward the paddle or reward rail visually if feasible.
- Auto-collected rewards should prioritize readability over showing every event as a separate line.
- If only 1-2 rewards auto-collect, show them individually:
  - `Auto-collected: Permanent Core`
  - `Auto-collected: +3 Balls`
- If several rewards auto-collect at once, stagger or group them into a compact summary:
  - `Auto-collected: 3 rewards`
  - `Permanent: Crit Core`
  - `Temp: +3 Balls, +4 Damage`
- Stage-clear screen should include a compact summary of auto-collected rewards from that level.

Implementation direction:
- Track `level.collectedRewardLog`.
- Add entries for both manual catches and auto-collects.
- Show recent entries as floating text immediately.
- Pass a summary into the stage-clear bonus screen.

Acceptance criteria:
- Clearing a level while pickups are falling visibly tells the player what was collected.
- There is no mystery about whether a falling upgrade was lost.
- Auto-collect text stays readable even if several pickups resolve at once.

## 4. Reward Identity Visuals

Problem:
- Temporary, permanent, and run rewards are not distinct enough yet.

Decision:
- Reward block and pickup visuals need stronger category language.

Suggested visual language:
- Permanent: white/gold prism, `P`, strongest glow.
- Temporary: blue hourglass or timer-pip look, `T`.
- Run upgrade: gold/orange core, `R`.
- Instant: cyan burst, `I`.

Implementation direction:
- Strengthen reward block core rendering.
- Add small category label or icon in the block and pickup.
- Keep exact reward name hidden until catch if needed, but category must be clear before breaking the block.

Acceptance criteria:
- A player can tell permanent vs temporary before hitting the brick.
- A permanent block should be obvious even during multiball chaos.

## 5. Side Rails For Permanent And Temporary State

Problem:
- The top-right temporary indicator is not a good fit.

Decision:
- Show permanent upgrade progress in a left-side rail outside the block/playfield.
- Show temporary active effects in a right-side rail outside the block/playfield.

Layout direction:
- Left rail: permanent upgrades earned this run/profile.
- Right rail: active temporary effects and remaining duration.
- Keep the playfield clear.
- Target desktop 1080p layout first.
- Mobile and compact layouts are out of scope for v0.25.

Important wording:
- "Outside the block" means outside the active brick/playfield area, not covering bricks, balls, or boss attacks.
- Do not compromise the desktop layout to support small screens in this pass.

Permanent rail examples:
- `P Crit +1`
- `P Paddle +1`
- `P Core x3`

Temporary rail examples:
- `+3 Balls: 1`
- `+4 Damage: 2`
- `Shield: 1`

Acceptance criteria:
- Permanent upgrades are visible on the left.
- Temporary upgrades are visible on the right.
- Neither rail blocks the ball, paddle, boss HP, or upgrade choice UI.
- Rails are validated for desktop 1080p.

## 6. Stage-Clear Second-Chance Rewards

Decision:
- Reward pools should not offer coins.
- Stage-clear bonuses should not offer coins.
- Stage-clear bonuses should only offer a permanent upgrade when the level did not already grant one and the second-chance permanent roll succeeds.
- If the second-chance permanent roll misses, stage-clear should offer temporary rewards.

Reason:
- Coins feel bad because the broader coin system does not exist yet.
- Stage-clear should help smooth permanent reward dry spells without guaranteeing permanent power every level.
- Temporary rewards are acceptable as the fallback when the permanent roll misses, as long as they are clearly labeled and expire predictably.

Stage-clear flow:
- Check whether the current level already granted a permanent upgrade.
- If yes, show temporary choices only.
- If no, roll the level's permanent reward chance again.
- If the roll succeeds, show permanent upgrade choices.
- If the roll misses, show temporary upgrade choices.

Important:
- Do not show coin choices in v0.25.
- Do not generate coin pickups in v0.25.
- Permanent stage-clear rewards should use the same clarity treatment as caught permanent pickups.
- Temporary stage-clear rewards must clearly show duration.

Acceptance criteria:
- No in-level reward block gives coins.
- No stage-clear choice gives coins.
- Stage-clear permanent choices only appear after a no-permanent level and a successful second-chance roll.
- Stage-clear temporary choices are clearly labeled as temporary.

## 7. Hearts, Life Loss, And Shield Feedback

Problem:
- `Lives 3` is easy to miss during fast play.
- Losing a life can feel abrupt.
- Shield saves need to look different from real life loss.

Decision:
- Replace the plain lives HUD text with hearts.
- Add a short life-loss animation.
- Add a distinct shield-shatter animation when a shield absorbs danger.

Behavior:
- Hearts show remaining lives clearly.
- Lost hearts can appear empty, cracked, or briefly pop before settling.
- A life-loss beat should briefly pause or soften the action before relaunch.
- A shield save should flash the paddle/player area and show shield shards instead of a heart loss.
- Shield charges must stay visually distinct from hearts.

Acceptance criteria:
- The player can tell at a glance how many lives remain.
- The player can immediately tell whether they lost a heart or spent a shield.
- The animation clarifies the hit without making the game feel slow.

## 8. Boss Attack Frequency Reduction

Problem:
- Bosses can steal attention from the brick-breaker flow too early.
- Level 10 should be a first boss check, not a projectile wall.

Decision:
- Scale down boss attack cadence across the game, especially for early bosses.
- Use clearer and slower attack patterns rather than frequent overlapping pressure.

Initial tuning targets:
- Level 10 Mossback Golem: heavy nerf, around 40-50% of current attack frequency.
- Levels 20-30: strong nerf, around 55-65% of current attack frequency.
- Levels 40-50: moderate nerf, around 70-80% of current attack frequency.
- Levels 60-80: lighter nerf, around 85-90% of current attack frequency.
- Levels 90+: minimal nerf, around 90-95% of current attack frequency unless playtests still feel too aggressive.

Implementation direction:
- Add boss attack pace multipliers by level band or a smooth level-scaling curve.
- Increase early boss cooldowns.
- Increase initial boss cooldowns so the player gets a few seconds of ball control.
- Reduce early phase escalation pressure if cooldown changes are not enough.
- Keep later bosses meaningfully threatening, but reduce the baseline spamminess across the board.

Acceptance criteria:
- A Level 10 death feels readable and earned, not random.
- Bosses still matter, but they do not drown out paddle, ball, and reward decisions.
- Later bosses can still ramp after the player has more upgrades, just with less oppressive attack cadence.

## 9. Cannon Controls And Readability

Problem:
- The cannon button is hard to use during fast play.
- The player needs to know whether they have the cannon and whether it can currently fire.

Decision:
- Change cannon firing to `Space`.
- Add a stronger cannon owned/ready/locked indicator.

Behavior:
- `Space` fires the cannon when it is available.
- `Space` is cannon-only and should not launch held balls.
- Cannon remains locked before the first ball launch.
- Indicator clearly shows:
  - Cannon not owned.
  - Cannon owned but locked.
  - Cannon owned and ready.
  - Cannon on cooldown or spent.
- The indicator should pulse or flash briefly when the cannon becomes ready.

Possible indicator treatments:
- A lower-HUD cannon icon with charge/cooldown fill.
- A compact icon near the paddle so the player sees it while tracking the ball.
- A locked state before first launch so the player knows why `Space` did nothing.

Acceptance criteria:
- Player can fire cannon with `Space`.
- Pressing `Space` without a ready cannon does not launch held balls.
- Player can tell cannon readiness without reading a small button.
- Cannon cannot fire before balls have launched.

## 10. Paddle Size Balance Pass

Decision:
- Make the paddle one-third smaller in v0.25.

Reason:
- With more balls, reward blocks, permanent progression, and safer boss pacing, paddle positioning can matter more.
- The current paddle is too large for dodging boss attacks cleanly.

Implementation direction:
- Reduce the base paddle width by about 33%.
- Confirm paddle-size upgrades still scale from the new base width.
- Verify the reduced paddle does not make the first few levels or Level 10 feel unfair.

Acceptance criteria:
- Base paddle is visibly smaller.
- Paddle upgrades still feel valuable.
- Boss projectile dodging has more room around the paddle.
- Difficulty increase feels intentional rather than punishing.

## 11. Save and Log Behavior

Keep the v0.24 checkpoint rule:
- Mid-level pickups are staged.
- Durable progress commits only on level clear.
- Quitting mid-level reloads the last committed loadout.

Add:
- `level.collectedRewardLog` for display only.
- `activeRun.permanentRewardLog` or profile permanent upgrade counts if needed for the left rail.
- Stage-clear summary should be generated from the current level's collected reward log before clearing transient level state.

Acceptance criteria:
- Reward clarity UI does not require saving live pickup entities.
- Reload behavior remains simple and exploit-resistant.

## Review Notes

Overall assessment:
- This is a strong v0.25 because the changes all support the same thing: clearer feedback and less "what just happened?" frustration.
- The biggest risk is that it is a broad release. Reward clarity, HUD layout, boss pacing, cannon input, and paddle sizing all touch game feel at once.
- The second biggest risk is mixed difficulty pressure: frequent permanent rewards and slower bosses make the game easier, while a one-third smaller paddle makes catches harder but boss dodging cleaner.
- The safest implementation approach is to land the clarity changes first, then test the combat/balance changes together before final commit.

Concerns to watch:
- Side rails may need a separate mobile/compact redesign later.
- Floating text can become noisy during multiball if several pickups auto-collect at once; v0.25 should group or stagger text when needed.
- The permanent chance curve may still create dry spells if the level roll and stage-clear roll both miss several times.
- Temporary stage-clear rewards need strong labels so they do not feel like mystery power that vanishes.
- `Space` must be reserved for cannon only, so input handling should not let it trigger ball launch.
- A one-third paddle reduction is a major change and could make early catches feel harsher, but it should make boss attack dodging less cramped.
